# Task3 — переход на Event-Driven архитектуру

## 1) Какие проблемы и риски есть сейчас

1. **Сильная связность через синхронные REST-вызовы**  
   `core-app` и `ins-comp-settlement` зависят от доступности `ins-product-aggregator` в момент запроса. Любая деградация агрегатора или внешних API страховых компаний напрямую влияет на внутренние сервисы.

2. **Длинный критический путь запроса**  
   `ins-product-aggregator` собирает данные из нескольких страховых компаний «на лету». При росте числа страховых (с 5 до 10) увеличатся latency, таймауты и вероятность частичных ошибок.

3. **Пиковая нагрузка и fan-out эффект**  
   Один запрос потребителя к агрегатору может порождать множество внешних вызовов. При росте трафика это быстро приведет к нестабильности и очередям на стороне интеграций.

4. **Устаревание локальных реплик данных**  
   Обновление тарифов по расписанию (15 минут / раз в сутки) создает окна несогласованности: в `core-app` и `ins-comp-settlement` могут быть разные версии продукта/тарифа.

5. **Хрупкость ежедневной интеграции `ins-comp-settlement -> core-app`**  
   Суточная REST-выгрузка оформленных страховок дает риск потерь/дублей при повторных запусках, проблемах сети или таймаутах.

6. **Масштабирование ограничено синхронной моделью**  
   Сложно независимо масштабировать производителей и потребителей данных: при всплесках нагрузка «пробивает» всю цепочку сразу.


## 2) Предлагаемое решение (Event-Driven)

### 2.1. Общий подход

Перевести обмен данными между внутренними сервисами с polling/REST на **Event-Streaming через брокер сообщений** (например, Kafka-совместимый кластер).

- `ins-product-aggregator` становится **источником доменных событий** по продуктам и тарифам;
- `core-app` и `ins-comp-settlement` становятся **подписчиками** и поддерживают свои локальные read-модели из событий;
- передача оформленных страховок из `core-app` в `ins-comp-settlement` также переводится на события.

Это снижает связность, убирает жесткую зависимость от «момента вызова» и позволяет сглаживать пики нагрузки.

### 2.2. Событийные потоки

Рекомендуемые топики:

- `product-catalog-events`  
  События каталога: `ProductUpserted`, `ProductArchived`.
- `tariff-events`  
  Изменения тарифов: `TariffUpserted`, `TariffDeprecated`.
- `policy-issued-events`  
  Оформленные страховки: `PolicyIssued`.
- `policy-status-events` (опционально)  
  Изменения статусов полиса для downstream-обработки.

Практики:

- ключ сообщения: `productId`/`policyId` для упорядочивания в рамках сущности;
- `eventId` + `occurredAt` + `version` в payload;
- идемпотентная обработка у потребителей (защита от дублей).

### 2.3. Что оставить синхронным

- Взаимодействие `ins-product-aggregator` со страховыми компаниями (`REST/SOAP/GraphQL`) — остается синхронным на интеграционном крае.
- Пользовательские операции чтения/оформления в `core-app` остаются синхронными внутри API продукта.

Меняется именно **межсервисный внутренний обмен** данными.

### 2.4. Transactional Outbox — использовать

**Решение: да, использовать Transactional Outbox**, как минимум в:

- `ins-product-aggregator` (публикация событий каталога/тарифов),
- `core-app` (публикация событий оформленных страховок).

Причина: нужно избежать расхождения «данные в БД записаны, а событие не опубликовано» и наоборот.

Базовый паттерн:

1. в одной транзакции с бизнес-данными пишется запись в `outbox`-таблицу;
2. отдельный publisher (CDC/джоб) дочитывает outbox и публикует в брокер;
3. после подтверждения публикации запись помечается отправленной.

Для `ins-comp-settlement` outbox можно добавлять по мере появления исходящих событий.


## 3) Как изменить C4 Container-диаграмму в Task3

Ниже список правок для файла диаграммы из `Task3/context`.

1. **Добавить контейнер брокера событий**  
   Новый контейнер внутри границы InsureTech:
   - `event-broker` `[Container: Kafka-compatible cluster]`
   - назначение: Event Streaming между внутренними сервисами.

2. **Добавить outbox-компоненты (контейнеры/тех.элементы)**
   - `aggregator-outbox-publisher` (рядом с `ins-product-aggregator`);
   - `core-outbox-publisher` (рядом с `core-app`).
   На C4 можно отразить как отдельные контейнеры или как технологические подписи у сервисов (допустимы оба варианта).

3. **Заменить синхронные связи на асинхронные**
   - Убрать/деакцентировать `core-app -> ins-product-aggregator (REST, получение тарифов)`.
   - Убрать/деакцентировать `ins-comp-settlement -> ins-product-aggregator (REST, получение тарифов)`.
   - Добавить:
     - `ins-product-aggregator -> event-broker` (publish product/tariff events),
     - `event-broker -> core-app` (consume product/tariff events),
     - `event-broker -> ins-comp-settlement` (consume product/tariff events).

4. **Заменить ежедневный REST-запрос реестра страховок**
   - Убрать/деакцентировать `ins-comp-settlement -> core-app (REST, получение оформленных страховок)`.
   - Добавить:
     - `core-app -> event-broker` (publish `policy-issued-events`),
     - `event-broker -> ins-comp-settlement` (consume issued policies).

5. **Добавить технические пометки на связях**
   - `at-least-once delivery`;
   - `idempotent consumer`;
   - `partition key = productId/policyId`;
   - `retry + DLQ`.

6. **Сохранить существующие границы ответственности сервисов**
   Функциональная декомпозиция не меняется (по условию задания): меняется только способ интеграции между сервисами.


## 4) Как это учитывает целевую технологическую архитектуру из Task1

Из `Task1` видно, что целевая платформа предполагает высокую отказоустойчивость и масштабирование (мультизональность, зрелая эксплуатация, observability). Для Task3 это означает:

- брокер событий разворачивать отказоустойчиво (репликация между зонами, без SPOF);
- мониторинг потоков (лаг consumer-групп, DLQ, error-rate) включить в контур наблюдаемости;
- масштабировать потребителей (`core-app`, `ins-comp-settlement`) независимо по lag/throughput, а не только по HTTP-нагрузке.

Такой переход снимает текущие узкие места polling-модели и лучше готовит систему к росту числа страховых компаний и общего трафика.

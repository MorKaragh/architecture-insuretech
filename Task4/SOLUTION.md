# Task 4 — продажа ОСАГО: решение для ревью

Краткие описания и обоснования. Детали реализации на схеме контейнеров (C4) в `Task4/`.

## Контекст задачи

Нужно оформить **ОСАГО онлайн**: после заполнения данных по авто сервис опрашивает **все** доступные страховые; на экране предложения **появляются по мере ответа** каждой страховой; максимум ожидания ответа одной страховой — **60 с**; в пик — до **~2500** одновременных пользователей на сценарии создания заявки. Команда зафиксировала: отдельный **`osago-aggregator`** для интеграций со страховыми; прочая логика оформления — в **`core-app`**.

## Решение по `osago-aggregator`

### Роль

Единая точка **исходящих** интеграций по ОСАГО: создание заявки у страховой и опрос готовности предложения по **однотипным REST API** страховых. **`core-app`** не вызывает страховые напрямую по этому продукту.

### Своё хранилище

**Да, отдельное хранилище** (например, схема/БД PostgreSQL у сервиса).

**Обоснование:** нужны устойчивые идентификаторы заявок, соответствие внутренних и внешних id по страховым, статусы опроса, идемпотентность при ретраях и при перезапуске подов, аудит. Без этого несколько реплик aggregator’а не могут безопасно делить работу и восстанавливаться после сбоев.

### API наружу для `core-app`

**Синхронный контракт поверх HTTP** (REST или gRPC — на схеме указать фактический выбор).

Минимальный смысл операций (формулировки URI могут отличаться):

- создать сессию расчёта / заявку на котировки по данным клиента и авто;
- при необходимости — получить агрегированный статус и результаты по идентификатору сессии (если не используете только push в сторону `core-app`).

**Обоснование:** `core-app` остаётся оркестратором продуктового сценария; aggregator — специализированный адаптер к страховым с политиками таймаутов, лимитов и повторов.

### Интеграция `core-app` ↔ `osago-aggregator`

Выбор: **синхронные вызовы для старта** + **доставка обновлений по мере готовности предложений** одним из подходов:

- **вариант A:** `osago-aggregator` вызывает **webhook/callback** в `core-app` по мере получения ответа от каждой страховой;
- **вариант B:** `core-app` **короткий polling** состояния у aggregator;
- **вариант C:** **внутренний брокер** (например, Kafka) с топиком событий по котировкам ОСАГО, consumer — `core-app`.

**Обоснование:** требование «показывать сразу, как пришло» лучше сочетается с **push** (A или C), чем с одним долгим HTTP request–response от браузера до aggregator’а. Конкретный вариант на схеме должен совпадать с нарисованными стрелками.

*Связь с Task 3:* Kafka для каталога/тарифов и полисов остаётся отдельным контуром; для ОСАГО Kafka **не обязателен**, если выбраны callback или polling — тогда на схеме не усложняем без необходимости.

## API для веб-приложения (`core-app`)

- Команды сценария: создание сессии расчёта, при необходимости подтверждение выбора предложения — **REST** (как и остальной BFF-монолит).
- **Поток обновлений котировок** — **Server-Sent Events (SSE)** или **WebSocket** от `core-app` к браузеру, чтобы не держать один HTTP-запрос на все страховые до 60 с и не опрашивать весь список вручную с задержкой.

**Обоснование:** соответствует UX из задания; отделение «команд» и «потока событий» — обычная практика для live-обновлений.

## Интеграция веб ↔ `core-app`

- **REST** — для старта сценария и мутаций.
- **Отдельная стрелка на схеме** — для **SSE или WebSocket** (как требует формулировка задания при выборе не-REST для потока).

**Обоснование:** для потока котировок REST «длинным запросом» или только polling хуже по UX и нагрузке; явная вторая стрелка показывает средство доставки.

## Паттерны отказоустойчивости

| Паттерн | Где | Обоснование |
|--------|-----|-------------|
| **Timeout** | `osago-aggregator` → страховые | Верхняя граница ожидания **60 с** по ТЗ; без таймаута зависшие вызовы блокируют пулы и каскадно бьют по сервису. |
| **Timeout** | `core-app` → `osago-aggregator` | Предсказуемое время ответа API aggregator’а, изоляция от деградации нижележащего контура. |
| **Circuit breaker** | Исходящие клиенты к API страховых | Серия ошибок по одной страховой не должна бесконечно расходовать ресурсы и усугублять инцидент. |
| **Retry** | Идемпотентные операции (повтор получения статуса/предложения с тем же id) | Сетевые сбои; только с ограничением попыток и **идемпотентными** ключами заявки. |
| **Rate limiting** | Вход в `core-app` (пользователь/сессия), в `osago-aggregator` **per страховая** (и при необходимости глобальные лимиты) | Пик **2500** concurrent; защита квот страховых и предотвращение ситуации «один поток забирает все слоты», в духе описанных в контексте компании проблем с перегрузом. |

Паттерны отображены на схеме **обозначениями из библиотеки курса** на соответствующих взаимодействиях.

## Несколько экземпляров сервисов

- **SSE/WebSocket** требуют **привязки сессии к поду** (sticky sessions на балансировщике) **или** общего хранилища сессий/шины сообщений, иначе клиент может потерять поток при смене инстанса `core-app`.
- Состояние заявки ОСАГО хранится в **хранилище `osago-aggregator`**, чтобы любой под мог продолжить опрос и не дублировать необоснованно обращения к страховым.

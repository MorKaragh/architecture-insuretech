# Task 4 — чек-лист схемы (C4, контейнеры)

Отметь пункты по мере готовности. Схема — **доработка to-be из Task 3** + новый контур ОСАГО.

## База и стиль

- [ ] Взята актуальная **диаграмма контейнеров to-be** из Task 3 (Kafka, `ins-product-aggregator`, `ins-comp-settlement`, границы с внешними системами).
- [ ] Сохранены **нотация C4** и **единый стиль** (как в курсе: контейнеры, внешние системы, подписи технологий на стрелках).
- [ ] Граница **InsureTech Prod** (или аналог) содержит все внутренние контейнеры, относящиеся к заданию.

## Новый и изменённые контейнеры

- [ ] Добавлен контейнер **`osago-aggregator`** (технология, краткое назначение в описании).
- [ ] На **`core-app`** в описании отражено: оформление ОСАГО и API для веб-клиента по этому сценарию (если меняете подпись — обновите).
- [ ] **`ins-product-aggregator`** не «заменён» aggregator’ом ОСАГО: на схеме видно **два** разных сервиса у границы со страховыми (или явное пояснение, если рисуете иначе).

## Внешние системы

- [ ] **Системы страховых компаний** — связи с **`osago-aggregator`** по сценарию ОСАГО (два эндпоинта по ТЗ: создать заявку, получить предложение).
- [ ] При необходимости — **отдельные** стрелки к `ins-product-aggregator` для прежнего контура продуктов/тарифов (как в Task 3), без смешивания с ОСАГО на одной подписи без пояснения.

## Потоки: `core-app` ↔ `osago-aggregator`

- [ ] Стрелка(и) **`core-app` → `osago-aggregator`**: создание/ведение заявки на расчёт ОСАГО, протокол и краткая подпись операций (см. `SOLUTION.md`).
- [ ] Отражена **доставка результатов** от aggregator к `core-app` (callback, polling, внутренний брокер/очередь — как в вашем решении; подпись на стрелке).
- [ ] Если используете **Kafka** для событий по котировкам ОСАГО — брокер на схеме, топик/направление **PUB/SUB** подписаны.
- [ ] Если Kafka **не** используете для ОСАГО — на схеме **нет** ложной связи «Kafka — ОСАГО»; логика только по выбранным стрелкам.

## Потоки: веб ↔ `core-app`

- [ ] **`InsureTech Web` → `core-app`**: старт сценария ОСАГО (REST или как решите).
- [ ] **Поток обновлений по мере готовности предложений** — если **не REST**, отдельная **новая стрелка** (SSE / WebSocket / иное — по ТЗ задания 4).
- [ ] На стрелке к вебу указано назначение (например: поток событий по котировкам).

## Хранилища

- [ ] У **`osago-aggregator`** своё хранилище **или** явная подпись «без отдельной БД» + где тогда состояние (если так решите — редкий вариант).
- [ ] **`core-db`** / связь `core-app` — БД для сессий заявок, черновиков, выбранного предложения (если отражаете на уровне контейнеров).

## Паттерны отказоустойчивости (библиотека курса)

- [ ] На схеме использованы **обозначения из библиотеки** для: **Timeout**, **Circuit Breaker**, **Retry**, **Rate Limiting** (где применимо — не обязательно все на каждой линии, но заявленные в `SOLUTION.md` — **видны**).
- [ ] **Timeout** — минимум на исходящих вызовах **`osago-aggregator` → страховые** (связь с лимитом **60 с** в подписи или комментарии).
- [ ] **Rate limiting / bulkhead** — по смыслу нагрузки на страховые и на входе API (где отметили в решении).
- [ ] Легенда или вынесенные иконки паттернов читаемы при экспорте в PNG/PDF.

## Несколько экземпляров (комментарий на схеме)

- [ ] Комментарий или callout: **sticky sessions** / общее состояние сессии для SSE/WebSocket **или** иной способ не терять поток при нескольких подах `core-app`.
- [ ] Комментарий: состояние заявки ОСАГО **вне памяти одного пода** (БД у aggregator), чтобы любой инстанс мог продолжить работу.
